## 1. 存在理由、产品定位与核心原则

### 1.1 为什么存在

星河的存在建立在两条现实前提之上：

1. **大模型具有长期多样性**：不同模型在架构设计、编码实现、评审排错、长文档理解和成本上差异巨大，短期内不存在单一模型在所有任务上兼顾能力与成本最优。
2. **「厂家 harness + 厂家 LLM」组合最优**：官方 CLI/harness（如 Claude Code、Codex CLI）的提示词、工具格式、上下文压缩与自身模型深度耦合，能力上限通常优于第三方通用 harness；同时，订阅额度（如 Claude Max、ChatGPT Pro 的周期窗口）往往只能通过厂家自家 harness 使用，比按量 API 更具成本优势。

由此直接推导出星河的定位：

- **管理的最小单位是 Agent（harness + LLM）**，而不是底层模型 API。
- **Agent 必须按黑盒管理**：平台不接管厂家 harness 内部推理与工具步骤，只管理任务输入、正式输出、沟通边界、职责与额度。
- **跨厂家协作需要中立协议**：各厂家自带的 subagent 或云端协作只服务自家生态，且原生会话互不兼容；跨厂家交接必须落到与 harness 无关的**正式文件与版本**上。

因此，星河**不是**又一个通用 harness、**不是**模型 API 网关，也**不是**在单框架内调度裸 API 的多 Agent 编排库。

### 1.2 产品定义与价值优先级

**星河是「可视化工作台 + 多 harness Agent 协同框架」。**

它面向个人独立开发者，以及需要组织多个自主 Agent 完成软件研发、研究分析与写作的个人用户。解决背景重复交代、人工传话、职责混乱、额度难统筹、产物散落和结果难追溯的问题。

多样性带来的三类价值按以下优先级落地：

1. **能力分工（首版核心）**：把合适的工作派给擅长的 Agent，清晰记录分工理由、文件修改边界与跨 harness 交接，最终汇总验收。
2. **额度池与成本分层（首版建基）**：统一管理订阅周期窗口与按量预算，按任务难度匹配高/低成本成员，分派时可见余量与重置时间。
3. **交叉验证与 PK（首版保留基础异构评审，完整 PK 放第二版）**：利用不同模型的错误分布差异，用异构评审或独立分支 PR 对比提升最终质量。

### 1.3 五项核心原则

| 原则 | 产品含义 |
|---|---|
| 成员独立黑盒 | Agent 保留自己的 harness、运行环境、会话、工具与执行方式；星河只管输入、输出与协作秩序 |
| 职责与权限清晰 | 角色任命文件定义职责与方法论；任务文件定义唯一承办成员、目标、修改范围与验收标准 |
| 星型沟通管控 | 管理员位于中心，通过 `@成员` 分派与询问；成员仅向管理员交付、汇报或求助；**系统强制禁止成员之间互相 `@` 直接交接** |
| 文件为准固化 | 群组消息承担通知、指派与异步互动；正式约定、进度、结果、评审与交接全部以有版本的文档和产物为准 |
| 流转可追溯 | 分配、领取、交付、预检、评审、返工与验收均关联操作者、时间与固定文档版本 |

**保存不等于提交，提交不等于验收，在线不等于正在执行，消息送达不等于责任完成。**

### 1.4 已确认方向与实施建议

已确认：

- 核心形态为**可视化桌面 Web 工作台 + harness 协同框架**；结构兼顾第二版移动端/PWA。
- 管理主体是**管理员（人）**；自然语言交互由**管理员助理**角色辅助理解与起草。
- **管理员助理是可灵活替换的角色**（即普通成员领取助理任命）；**初版默认由 Codex CLI 担任**，可随时切换为 Claude Code、OpenCode 或其他支持同一协议的成员；核心系统完全脱离对特定 Agent 的强绑定。
- 助理具备**可配置权限等级**，初版默认设置为**人更多介入的权限**（起草和预检由助理完成，分配、退回、验收、改范围须人确认）。
- **成员模型**：每个成员拥有稳定 UUID；允许同一 harness 存在多个成员；**首版 1 个成员固定绑定 1 个 harness + 1 个模型**。
- 引入**额度池（Quota Pool）**，支持多个成员共享同一订阅账号/周期窗口或预算池。
- 交互采用类似邮件组的异步群聊视角（管理员看全组，成员只看自己与管理员往来），`@` 仅针对**成员**，不 `@角色`。
- Task 为顶层业务入口，不增加 Project、Workspace 业务层；流程、策略与决策内嵌于任务文件。
- 正式文档版本采用 **Git**；运行控制、身份授权、额度池、消息与查询采用 **SQLite**（区分不可丢失的权威表与可重建索引）；每个字段只有一个权威来源。
- **首版范围收敛**：聚焦本地 CLI（Codex CLI、Claude Code）的能力分工闭环（单任务、接力、多角色并行、基础异构评审返工）；常规协作靠任务分工避免改同一批文件。**PK（各自建分支提 PR 对比）** 与 **云端 Agent 接入（MCP/HTTP）** 明确划入第二版，协议预留扩展位。

本版实施建议：

- 常规状态流转、权限校验与星型消息路由由确定性程序负责，不依赖持续 LLM 会话；助理离线时，管理员仍可通过工作台表单与按钮完成全部操作。
- 后端优先 Go 单服务，前端保留 React/TypeScript 轻量组件（实施建议，不代表代码已完成）。
- 本地代理作为首版执行接入核心，负责拉起/管理本地 CLI 进程、准备输入与收取产物。
- 首版单服务、单正式 Git 写入者；Runner 用作本地执行与团队约定机制参考，尚未选为必需底座。

## 2. 核心业务概念

| 概念 | 定义与边界 |
|---|---|
| 管理员 Admin | 平台唯一最高决策者（人），拥有任务发布、分派、退回、验收、调整助理权限等级等最终权力 |
| 管理员助理 Assistant | 一种可灵活替换的角色，由被授予助理任命的普通成员担任（初版默认 Codex CLI）；在授权等级内解析自然语言、起草方案、预检交付、代查进度 |
| 成员 Member | 稳定的协作身份，以 UUID 标识；**首版固定绑定「1 个 harness + 1 个模型 + 运行配置」**，允许同 harness 创建多个成员（如 `Codex-助理` 与 `Codex-实现`、`Claude-Opus` 与 `Claude-Sonnet`） |
| 能力画像 Capability Profile | 成员擅长的任务类型标签（首版人工维护）及历史评审/验收表现记录，作为能力分工依据 |
| 额度池 Quota Pool | 订阅账号或计费预算池（如 Claude Max 5 小时窗口、ChatGPT Pro 窗口、API 预算）；多个成员可挂载至同一额度池共享消耗 |
| 角色 Role / Profile | 职责、方法论、工作原则和交付规范，可复用与版本化 |
| 任命文件 Appointment | 将某个角色（含「管理员助理」「架构」「实现」「评审」等）赋予某成员的正式文件；含职责边界与版本 |
| Agent Runtime | Codex CLI、Claude Code 等本地或远端执行环境，保留自身 harness、工具与原生会话 |
| 连接与执行实例 Connection / Instance | 带认证与授权范围的接入通道及在线运行端；首版聚焦本地实例，架构保留多实例与云端扩展能力 |
| 群组消息 Message | 星型异步沟通载体，分为管理员指令（5 类）与成员回报（3 类）；携带 `@成员` 与固定文件引用，不替代正式文件本身 |
| 任务 Task | 可交付工作的顶层入口，支持拆分为子任务与依赖关系；任务文件记录约定、分派理由、修改范围、进度、结果与引用 |
| 执行尝试 Run | 对任务的一次具体执行，具有独立 ID；重试或返工产生新的可追溯尝试 |
| 产物 Artifact | 代码变更、报告、测试证据等实际成果，使用固定代码引用或内容哈希标识 |
| 评审任务 | `kind` 为 `review` 的普通任务，引用待审交付的固定版本与标准，提交独立结论 |
| 交付 Submission | 一次显式提交形成的不可变任务版本与产物清单；最终完成须经管理员验收 |

一个执行任务同一时刻只有一个承办成员；需多人协作的复杂工作拆分为带依赖关系的关联子任务。同一成员模型若发生变更，建议新建成员并归档旧成员，避免能力画像与历史数据混杂。

## 3. 星型沟通、助理权限与正式文件

### 3.1 星型沟通拓扑

平台在界面上呈现类邮件组的异步协作流，但通信拓扑严格采用**以管理员为中心的星型结构**，并由系统在接口和工具层强制执行（不只依赖提示词约束）：

1. **管理员 → 成员（5 类指令）**：
   - **分配（Assign）**：附带固定版本的任命文件、任务文件与输入引用，唤醒成员开始执行。
   - **询问进度（Inquire）**：查询任务进展。**省额度默认规则：先由星河直接读取任务文件与运行状态回答，不唤醒 CLI**；仅在管理员明确选择「唤醒询问」时才触发 Agent。
   - **补充/澄清（Supplement）**：补充说明或调整约定，并产生新的任务文件版本。
   - **退回返工（Return）**：附带评审意见或问题清单，要求基于新轮次修正后重新交付。
   - **取消/暂停（Cancel / Pause）**：中止或暂停当前工作。
2. **成员 → 管理员（3 类回报）**：
   - **交付（Deliver）**：提交冻结的任务文件版本与产物清单，触发验收或下游流转评估。
   - **汇报（Report）**：上报关键里程碑或响应唤醒询问，不改变正式验收状态。
   - **求助/阻塞（Help / Block）**：遇到输入缺失、范围不清或环境阻碍，将任务标为阻塞并提醒管理员。
3. **成员 ↔ 成员（系统禁止）**：
   - **禁止成员之间互相 `@` 或直接交接任务**；成员侧可用工具仅允许向管理员发送回报。
   - 跨成员交接一律经由中心：成员 A 交付给管理员 → 管理员验收（或按授权放行）后，将 A 的固定交付版本作为输入分配给成员 B。评审结论亦先交回管理员，再由管理员决定退回给 A 或直接验收。
4. **`@` 规则**：
   - `@` 仅指向具体**成员**（如 `@Codex-实现`、`@Claude-Sonnet`），不支持 `@角色`；角色通过角色任命文件定义。

### 3.2 管理员助理与权限等级

管理员助理是持有「管理员助理」任命文件的普通成员（初版默认 Codex CLI，随时可换为其他成员）。助理的操作严格受**权限等级**约束，且任何代发或起草记录均明确标注实际执行成员：

| 权限等级 | 定位 | 助理可执行动作 | 必须由管理员（人）确认/执行 |
|---|---|---|---|
| **L1 辅助起草（初版默认）** | 人更多介入，可控优先 | 理解自然语言、起草任务拆解与分工建议、预检成员交付并生成摘要、代查静态进度 | 所有任务发布、正式分配、补充变更、退回返工、取消、最终验收 |
| **L2 计划内流转（可选）** | 半自动推进 | L1 全部能力 + 在已批准计划内按依赖自动转派下一步、常规唤醒询问 | 变更任务范围、调整分工计划、退回争议处理、最终验收 |
| **L3 高自主托管（远期）** | 规则内闭环 | L2 全部能力 + 按预设标准触发常规返工与复审 | 异常仲裁、预算超限授权、最终交付验收 |

### 3.3 两类核心正式文件

| 文件 | 必需内容 | 写入职责 |
|---|---|---|
| 角色任命文件 | 任命 ID/版本、成员 UUID、角色（如助理/架构/实现/评审）、职责、方法论、权限边界、交付规范 | 管理员发布（助理可起草草稿） |
| 任务文件 | 任务 ID/版本、承办成员、分派理由、任命引用、目标、修改文件范围（file_scope）、输入、验收标准、流程、进度、结果、产物与遗留项 | 管理员维护任务约定；承办成员更新执行进度与结果；平台校验正式提交与受保护字段 |

评审复用任务文件。长报告与大文件作为任务文件引用的产物保存。成员不可覆写已提交版本，也不能私自修改受保护字段完成验收。正式正文采用 Markdown + 结构化 YAML 头部，路径便于阅读，文档 ID 与固定 Git commit 为交接依据。

### 3.4 星型上下文隔离边界

- **管理员视角**：工作台展示任务下所有成员与管理员的往来总览，可按成员筛选查看一对一通道。
- **成员视角**：成员被唤醒时，**仅获得自己与管理员的往来消息，以及本次任务明确指定的固定文件版本**：
  1. 当前任命的固定版本；
  2. 当前任务约定、修改范围与流程；
  3. 管理员明确附带的输入文件、前序交付版本或评审意见；
  4. 与当前任务有关的正式澄清记录。
- 默认不注入其他成员的会话、聊天记录、工具调用过程或草稿。外部材料需记录来源、获取时间与校验信息；输入在任务发布时冻结，变更须发布新约定版本。

### 3.5 业务数据归属与版本规则

**Git 保存正式约定、任务成果和业务变更依据；SQLite 权威表保存成员、额度池、权限、星型消息与执行控制事实；SQLite 投影表只读派生自 Git；大产物按内容哈希或固定代码引用保存。**

| 业务数据 | 唯一权威来源 | 说明 |
|---|---|---|
| 角色模板、任命文件、任务约定、分派理由、修改范围 | Git 文档 | 索引只读投影，不能独立改写 |
| 正式里程碑、阻塞说明、结果报告、评审意见、交付清单、验收/退回结论 | Git 文档与业务记录 | 经正式提交与授权动作追加提交 |
| 成员 UUID、harness 与固定模型配置、能力标签、启停 | SQLite 权威表 | 任命文件仅引用成员 UUID |
| 额度池定义、周期规则、消耗记录与手动校准值 | SQLite 权威表 | 支持多成员共享挂载，独立备份 |
| 助理任命绑定与权限等级配置（L1/L2/L3） | SQLite 权威表 + Git 任命 | 权限开关实时生效于数据库；职责说明存于 Git |
| 星型群组消息、待确认助理草稿、通知投递 | SQLite 权威表 | 正式交付/变更消息关联固定 Git commit |
| 连接认证、授权范围、实例状态、Run、租约、代际编号、幂等记录 | SQLite 权威表 | 原子领取与防旧写，不可由 Git 重建 |
| 实际执行耗时、可获取用量与费用记录 | SQLite 权威表 | 未知费用显式标记，不填零冒充已知 |
| 文档列表、全文检索、依赖图、任务业务状态投影 | SQLite 可重建索引 | 只由投影器从 Git 重建，带源 commit |
| 代码快照、长日志、图片、数据集等实际字节 | 原代码仓库或内容寻址存储 | Git 清单仅记录固定引用与内容哈希 |
| 未提交草稿、编辑器自动保存 | 草稿文件存储 | 不是正式版本，不触发下游 |

写入与恢复原则：

- 正式文档由星河统一串行提交 Git，首版只追加不改写历史；普通保存、心跳、原生日志不产生 Git commit。
- Git 与 SQLite 无共享事务：发布须记录幂等 command、候选 commit 与恢复状态，对账完成后才推进下游。
- 索引损坏可从 Git 重建；SQLite 权威表与大产物须随 Git 一同纳入备份恢复体系。
- API Key 等密钥不进入 Git、正式文档、前端产物或常规日志。

## 4. 协作模式与工作流

### 4.1 基本闭环

```
管理员自然语言/表单提出目标
  → 助理(L1)拆解子任务、推荐分工与文件范围、生成草稿
  → 管理员确认发布并 @成员 分配
  → 成员读取固定文件自主执行（期间可 @管理员 汇报或求助；管理员可静态/唤醒询问）
  → 成员 @管理员 交付（冻结任务版本与产物清单）
  → 助理自动预检并给摘要
  → 管理员决定：验收 / 退回返工 / 验收并转派下游（含异构评审）
```

### 4.2 支持的协作方式与分期

| 协作方式 | 分期 | 说明 |
|---|---|---|
| 单 Agent 执行 | **首版** | 管理员分配明确输入，成员自主执行、交付、验收 |
| 跨 harness 接力 | **首版** | 成员 A 交付并经管理员验收后，由管理员将固定交付版本分配给成员 B |
| 多角色并行分工 | **首版** | 大任务拆为多个无文件重叠的子任务并行执行，分别交付管理员汇总 |
| 执行 + 异构评审返工 | **首版** | 不同模型/harness 成员执行独立评审任务；结论交回管理员后决定退回或验收 |
| 不同 Agent / Profile PK | **第二版** | 冻结共同输入与标准，各竞争成员**各自建立独立 Git 分支并提交 PR**，独立隔离对比评审 |
| 方案融合 | **第二版** | 针对 PK 评测结果新建融合任务，保留原方案不覆盖 |

### 4.3 交接内容与代码隔离

- **正式交接包**至少包含：任务目标、已完成事项、事实与假设、关键设计选择、输入与产物固定版本、验证结果、遗留问题及下一步建议。
- **首版常规协作代码隔离**：通过清晰的任务拆解与任务文件中的 `file_scope`（修改文件范围）避免多个成员同时改同一批文件；必要时由管理员指定工作目录。
- **第二版 PK 代码隔离**：星河协调或要求各竞争成员在独立 Git 分支开展实现并提交 PR，确保提交前互相隔离、评审可逐行对比。

### 4.4 评审与返工规则

评审任务独立建档，引用固定 `submission_id` 与产物哈希，绝不修改原作者报告。原作者返工后生成新的 Run 与交付版本，旧评审记录永久保留且不会自动覆盖新版本。

## 5. 状态与触发规则

任务状态拆分为两个权威来源独立的维度，禁止双向写入同一状态字段：

| 维度 | 示例 | 权威来源 |
|---|---|---|
| 正式业务阶段 `business_state` | 已发布、已提交、评审中、待修订、待验收、已完成、已取消 | Git 任务文件及正式变更记录 |
| 执行状态 `run_state` | 排队、启动中、运行中、阻塞、停止中、已退出、失败、待核实 | SQLite Run、租约和实例记录 |
| 派生显示状态 | 可领取、等待依赖、阻塞待澄清、提交同步中 | 综合以上两类事实派生，不可写 |

触发规则：

- 触发业务推进的仅限正式动作：**发布/分配、交付、评审提交、验收、退回、取消**。
- 普通草稿保存、心跳、进程退出、一般汇报与静态进度查询**不触发业务流转**。
- 取消任务先在数据库阻断新领取并发送停止意图，再向 Git 写入正式取消结论；进程是否实际终止以 Run 事实为准。

## 6. 成员、额度池与本地接入

### 6.1 成员与额度池规则

- **首版绑定规则**：1 个成员 = 1 个 harness + 1 个固定模型 + 运行配置。同一 harness 可创建多个成员；例如同时用 Codex CLI 担任助理与实现时，可建 `Codex-助理` 和 `Codex-实现` 两个独立成员，上下文与任命隔离。
- **额度池共享**：多个成员可绑定同一额度池（如 `Claude-Opus` 与 `Claude-Sonnet` 共用 `Claude Max` 池；`Codex-助理` 与 `Codex-实现` 共用 `ChatGPT Pro` 池）。
- **额度数据来源（首版务实策略）**：支持配置池类型（周期窗口订阅 / 按量预算）与重置规则，自动累计星河内调度的任务数、运行时长及 CLI 可返回的用量信息，并支持管理员**手动校准**当前剩余比例或重置时间；未知真实余量时明确标示「估算/待校准」。

### 6.2 接入路径与执行权控制

- **首版主路径（本地 CLI）**：由星河本地代理管理 Codex CLI、Claude Code（及可选 OpenCode）进程，按参数数组非交互启动或按需恢复会话，传递受限授权的输入文件包，收取候选产物并记录退出事实。
- **第二版扩展（云端 MCP/HTTP）**：保留同一套文档、星型回报与提交协议，允许具备网络和工具调用能力的云端 Agent 接入；唤醒寿命由云端宿主负责。
- **唯一执行权**：服务端通过 SQLite 事务、租约与单调递增 `lease_epoch` 保证同一任务同一时刻最多一个有效执行实例；旧实例迟交的结果归档留证，绝不覆盖当前正式交付。

## 8. 可视化工作台

桌面 Web 工作台围绕「能力分工 + 星型沟通 + 文件产物」组织为三栏结构（详见原型 `prototype/workbench.html`）：

- **顶部栏**：任务导航与状态、当前**管理员助理徽章与权限等级切换入口**（直观展示当前助理成员如 `Codex-助理 · L1 辅助起草` 并支持切换）、搜索与新建操作。
- **左栏（资源与进度）**：
  - **协作成员列表**：展示成员名称、角色徽标、harness + 固定模型、所属额度池、运行状态与能力标签；点击可筛选对应成员的一对一通道或高亮其负责任务。
  - **额度池面板**：展示各池共享成员、已用比例/估算、重置倒计时与校准入口。
  - **子任务进度概览**：快速定位各子任务状态与承办成员。
- **中栏（协作主区，三视图切换）**：
  - **星型协作流**：管理员总览所有成员往来（支持按成员筛选），展示助理起草确认卡、正式交付/验收事件卡、代码 diff 与预检摘要；底部输入框支持选择管理员指令类型（分配、静态/唤醒询问、补充、退回、取消、找助理起草）并 `@成员`。
  - **分工视图**：按阶段列展示子任务卡片与依赖连线，每张卡片同时显示 `业务状态(Git)`、`执行状态(DB)`、承办成员、**分派理由**与**文件修改范围**。
  - **任务文档**：完整查看/编辑当前任务 Markdown 文件，明确标识草稿/正式版本与受保护字段，提供版本对比、验收、退回按钮。
- **右栏（产物与固定版本预览）**：按全部/文档/代码/评审筛选产物列表，下方实时预览代码或 Markdown，明确区分草稿与已冻结的 commit/哈希版本。

第二版再补齐移动端/PWA 轻量阅读、审批与通知体验；PWA 不承担本地 CLI 运行。

## 9. 非功能要求

- **可靠性**：Git 正式历史只追加；Git 与 SQLite 之间通过持久化 command、候选 commit 与恢复对账保证不丢交付、不重复派工；未知状态的外部执行绝不盲目重跑。
- **强约束与权限边界**：星型沟通（禁止成员互 `@`）、受保护文档字段、成员上下文读取范围、助理 L1 确认门禁均由服务端程序强制校验，绝不依赖提示词自律。
- **安全性**：凭据不入 Git、任务正文、前端产物或常规日志；文件读取与收取校验路径与权限；外部文档正文不可提权。
- **可观察性**：日常只展示关键里程碑、阻塞、交付与验收事件；原始 CLI 日志收归诊断入口；断线、租约失效与进程退出分别记录。
- **可维护性与平台兼容**：文档含 `schema_version`；核心协议与存储完全不绑定特定助理模型或 CLI；用户明确包含 **Windows** 环境，CLI 启动、进程树停止与路径处理须在 Windows 实机验证。

## 10. 技术建议与分期范围

| 层次 | 本版建议 | 说明 |
|---|---|---|
| 前端工作台 | React + TypeScript，轻量组件 | 三栏桌面优先，预留 PWA 路径 |
| 业务核心服务 | Go 单体服务 | 负责星型路由、文档发布、权限、额度池、领取与对账 |
| 正式文档库 | Git（服务集中提交） | 管理角色、任命、任务、交付清单与变更记录 |
| 运行与检索 | SQLite（权威表 + 可重建投影） | 权威表单独备份；后续按需评估 PostgreSQL |
| 大产物与草稿 | 原代码仓库 / 内容寻址文件存储 / 草稿目录 | Git 仅记录固定引用与内容哈希 |
| 管理员助理 | 任意支持协议的成员（**初版默认 Codex CLI**） | 角色可替换；不绑死 OpenCode 或特定模型 API |
| 执行接入 | 本地代理适配 Codex CLI、Claude Code | 按锁定版本验证非交互启动与进程管理 |

- **首版聚焦**：可视化三栏工作台、本地 Codex CLI / Claude Code 接入、Codex CLI 担任默认可替换 L1 助理、成员与额度池管理、星型 `@成员` 沟通、单任务/接力/并行/异构评审返工、Git+SQLite 正式版本与恢复。
- **第二版计划**：PK（各自建分支提 PR 评审）、云端 Agent（MCP/HTTP）、L2/L3 自动化流转、移动端/PWA、更多 Agent 与跨主机部署。
- **暂不建设**：Project/Workspace 业务层、自由群聊社交系统、通用图形化工作流引擎、Agent 市场、跨厂家原生会话迁移、多服务集群。

## 11. 验收标准

| 编号 | 可验证标准 |
|---|---|
| AC-01 | 任命与任务文件完整包含职责、目标、分派理由、修改文件范围、输入与验收要求 |
| AC-02 | Codex CLI 与 Claude Code 均可作为成员按任务文件完成工作并提交可打开的报告与产物 |
| AC-03 | 支持同一 harness 创建多个绑定固定模型的成员，且多个成员可共享同一额度池并在分派时可见余量与重置时间 |
| AC-04 | 系统强制禁止成员间互相 `@` 或直接交接；跨成员交接必须经管理员验收/转派并绑定固定交付版本 |
| AC-05 | 成员被唤醒时仅获得自己与管理员的往来及明确指定的固定文件，无法读取其他成员消息或未授权任务 |
| AC-06 | 管理员使用「静态询问进度」时直接基于文件与运行状态回复，不唤醒 CLI、不消耗额度 |
| AC-07 | 初版由 Codex CLI 担任管理员助理并在 L1 权限下仅能起草与预检，任何正式发布、分配、退回、验收须经管理员确认 |
| AC-08 | 更换持有「管理员助理」任命的成员即可切换助理（如 Codex ↔ Claude/OpenCode），且助理离线时全部固定操作仍可手动完成 |
| AC-09 | 接手者仅凭固定交付文档与产物引用即可继续工作，无需重述关键背景 |
| AC-10 | 异构评审任务指向固定交付版本，支持退回返工并保留历次交付与旧评审，不互相覆盖 |
| AC-11 | 保存草稿、一般汇报与心跳不触发下游；已提交也不自动显示验收通过 |
| AC-12 | 关闭 UI 后执行可继续，重开后准确恢复业务阶段与运行状态 |
| AC-13 | 重复发布、提交或通知不产生重复执行或重复下游任务 |
| AC-14 | 缺产物、写入未完成、异常退出、阻塞和存活未知分别明确处理 |
| AC-15 | 新尝试开始后，旧实例迟交结果仅归档留证，不能覆盖当前正式交付 |
| AC-16 | 取消、返工与输入变更均保留操作者、原因和版本关系 |
| AC-17 | 恢复时不自动重跑运行情况不明且可能有外部副作用的任务 |
| AC-18 | 凭据不出现在正式文档、前端构建产物和常规日志中 |
| AC-19 | 旧版本写入冲突返回明确冲突错误，不能静默覆盖新内容 |
| AC-20 | 重命名路径不破坏 ID/版本引用；从最终交付可完整追溯任命、输入、执行、评审与验收依据 |
| AC-21 | Git 已发布但数据库收尾失败时可对账恢复，不重复交付或派工 |
| AC-22 | 直接篡改索引、草稿或任命正文权限说明，无法绕过实际授权、星型限制或正式验收 |
| AC-23 | 从 Git 重建索引不丢权威运行表与额度数据；备份恢复须同时覆盖 Git、权威表与大产物 |
| AC-24 | 在目标平台（含 Windows）完成 CLI 启动、停止、Git/SQLite 故障对账实测验证 |

## 12. 讨论演进与版本变更

| 讨论主题 | 本轮结论（v0.5） | 对产品与设计的影响 |
|---|---|---|
| 存在理由 | 大模型多样 + 厂家 harness+LLM 能力与订阅成本最优 | 管理单位定为黑盒 Agent；星河定位为「可视化工作台 + harness 协同框架」 |
| 价值排序 | 首版最看重能力分工，其次额度池，评审保底，完整 PK 放第二版 | 首版聚焦单任务、接力、并行与异构评审；工作台突出分工理由与文件范围 |
| 成员与额度 | 同 harness 可多成员，首版 1 成员绑定 1 固定模型；新增额度池 | 支持 `Codex-助理`/`Codex-实现`、`Claude-Opus`/`Claude-Sonnet` 共享订阅池 |
| 管理员助理 | 可灵活替换的普通角色，初版用 Codex CLI；设置权限等级（初版默认 L1） | 取消 OpenCode 硬绑定，统一走成员协议与确认门禁 |
| 沟通与流转 | 类邮件组星型群聊 + 文件核心流转；仅 `@成员`；系统禁成员互 `@` | 修正 v0.4「完全去群聊」的偏差，同时保住可控性与省 token 隔离 |
| 代码隔离 | 首版靠分工与文件范围避冲突；第二版 PK 各自建分支提 PR | 降低首版复杂度，明确第二版 PK 工程路径 |

- **v0.5（2026-11-25）**：补齐产品存在理由；确立「可视化工作台 + harness 协同框架」定位；改为星型沟通（禁成员互 `@`）+ 文件核心流转；明确首版 1 成员绑定 1 固定模型与额度池；将助理改为可替换角色（初版默认 Codex CLI）并分级授权（L1 默认）；收敛首版范围至本地 CLI 能力分工，PK（独立分支提 PR）与云端接入划入第二版。
- **v0.4（2026-11-25）**：确定 Git 正式版本；数据库明确分为权威运行表与可重建索引；拆分业务阶段与执行状态；增加跨存储恢复与备份要求。
- **v0.3（2026-11-25）**：确立角色任命与任务文件分离、显式提交、不可变交付、独立评审、租约唯一领取与 Go 核心实施建议。
- **v0.2（2026-11-02）**：初版任命书/报告、OpenCode + DeepSeek、轻量 CLI 桥接及文件优先构想。
